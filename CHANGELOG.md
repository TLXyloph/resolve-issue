## [1.0.0] - 2026-10-14

The first public release.

### Added

- `/resolve-issue <issue-url>` takes one GitHub issue to a validated, ready-to-open pull request. A skill sizes the run and launches the `resolve-issue:pipeline` dynamic workflow, which does the work.
- Four modes trade speed and cost against depth:
  - `triage` reads the issue thread, prior art and viability only, with no clone.
  - `quick` reproduces, plans and scopes in one step, fixes, and runs one combined skeptical check. A check that passes but never reaches the differential is not a failure: the next attempt keeps the code.
  - `standard` (the default) adds a separate scope step, a feasibility spike with re-scoping, and separate verify and confirm steps.
  - `thorough` adds a polish pass that a fresh agent re-checks, two extra independent reviewers, more attempts and the full test suite.
- Effort levels (`low`, `medium`, `high`, `max`, `inherit`) set how hard each class of agent thinks.
- `model=<alias or ID>` runs every pipeline agent on one model; Vertex IDs (`…@…`) and Bedrock ARNs work too. Without it, agents use the session's model.
- A hard agent cap per mode, adjustable with `maxAgents=N` (4 to 200). A run that reaches it stops with `agent-budget-reached` and a resume hint. Thorough mode's extra reviewers take only the slots the cap leaves after one for the final check, so near the cap the packet comes back without them and a warning says so. They start before the final check, so a resume that re-runs only the final check replays them from cache. At the maximums (`attempts` 8, `maxAgents` 200), a stop says a resume cannot go further instead of asking for more. A run whose Claude Code token budget for the turn runs out stops with `token-budget-reached`.
- Argument checks: `attempts` (1 to 8) or `maxAgents` (4 to 200) outside its range stops the run with `bad-args` instead of being adjusted.
- A cost question before each run. It shows the mode, effort, model, the typical and maximum agent counts and the time and tokens measured for the mode, and offers a cheaper alternative. `yes` or the `confirm_before_run` option skips it. `yes` never approves a publish.
- A viability check before any expensive work. It stops on a closed issue, a competing pull request updated in the last 30 days, a claim, work in progress, a `wontfix`, `invalid` or `duplicate` label, an archived repository, or a repository that rejects AI-assisted contributions. `force` overrides only the soft stops. Hard stops are reported first, so a stop offers `force` only when every stop is soft.
  - `claimed`: a claim up to 7 days old, or up to 14 days old with a PR, a branch or a maintainer's acknowledgement. A claim this recent, or one of unknown age, is presumed active. Older claims only add a warning.
  - `work-in-progress`: an unmerged change to the project's own code that fixes the issue without a PR (a branch or a commit referencing the issue, in the repository or a fork), touched in the last 60 days or at an unknown time. Older work only adds a warning. A workaround in another repository does not count.
- Clone discovery: the pipeline uses an existing clone in or under the current directory (any remote that points at the repository). If none exists, it clones with `--filter=blob:none` into the current directory, or next to the enclosing repository when the current directory is inside an unrelated one: next to its main clone, also when the current directory is a worktree such as Claude Code's `.claude/worktrees/<name>`, and next to the main clone of the outermost superproject when it is in a submodule, nested or not. In a main working tree the main clone is that checkout; from a linked worktree, it comes from the first entry of `git worktree list`: that entry's checkout (also for a worktree of a submodule), or the entry itself for a bare repository or the git dir of a `--separate-git-dir` clone.
- A per-worktree environment: when none exists, as in a fresh clone, validation creates one for the worktree only. For Python, that is a virtualenv in `<worktree>/.resolve-issue/venv` with an editable install of the worktree and its test dependencies. Node uses the lockfile install inside the worktree; Rust and Go use the toolchain's fetch. The validation agent is told never to install into the main clone's environment, a shared virtualenv or the global environment. When a service or toolchain the tests need is missing, the run stops with `validate-blocked`, which a resume with `validateAttempt` retries.
- Reproduction first: the pipeline reproduces the issue at the base and writes an acceptance test before it changes any code. For a behavior fix, that test fails on the base; if no test can be made to fail, the run stops with `no-red-test`. `invalid-issue` is only for an issue that is not a defect or is already fixed.
- An independent check: a fresh agent re-proves the fix with a differential, red on the base and green with the fix. It runs the acceptance test, the reproduction and the regression test the fix added to the repository's own tests, and saves the output as evidence (`base-*.txt`, `head-*.txt`). The base side runs at the branch's merge-base with the fetched base. The pass rule depends on the change kind (behavior, diagnostics or docs) and fails closed: a field the checker leaves out never counts, and a change is judged as docs only when the checker reports that no code changed. A behavior change needs both tests to fail on the base. After a polish pass, a fresh agent re-checks the polished head the same way; if that fails, the packet carries a blocker finding and names the last confirmed head. A head the final check reports that no differential proved gets a warning. When a polish pass ran without reporting a valid merge, such a head is also a blocker, because polish commits may be in it.
- A scope gate. The run halts and asks when the responsible fix goes beyond the literal ask. The halt returns `gateKey` and `earlierDecisions`; a resume passes `scopeDecisions` with every earlier decision plus `{ key: gateKey, answer: "proceed" | "abort" }`. Each gate takes only the answer with its own key.
- Contribution rules: the pipeline reads CONTRIBUTING, AGENTS.md, the PR template and DCO or CLA rules, and follows the repository's commit and PR conventions.
- A built-in final check: wider tests, lint on changed lines, a maintainer-eye review with findings, and a drafted PR title and body. The review receives the independent checker's notes and confirms or dismisses each one as a finding. Findings that report the same problem (same file, first line number and description opening) are merged at the higher severity and recommendation, with the other wording kept in `alsoReported`.
- An optional [no-mistakes](https://github.com/kunchenguid/no-mistakes) gate for repositories already set up for it, run with push, PR and CI skipped. Thorough mode's extra reviewers run beside it; their findings appear as `gate.reviewFindings`, numbered `RV1`, `RV2`, ... The gate agent recommends an action for each no-mistakes finding. It also checks the independent checker's notes against the diff, and the real ones join `gate.reviewFindings`. A run that is still going stops with `gate-still-running`, and a resume with `gateAttempt` reattaches to it. The gate agent starts each validation run in no-mistakes' strict launch mode. It records the run id from the run's launch receipt in `.resolve-issue/validation-runs.txt`. It reattaches only to a recorded run. A run that started and failed stops with `handoff-failed` and shows the failed step and its findings. The intent quotes the issue title as data.
- An explicit `gate=no-mistakes` on a repository where no-mistakes is not installed or not initialized stops with `handoff-failed` right after recon, before the worktree. A resume with `gateAttempt` continues the run, and the gate checks no-mistakes live.
- An approval packet that shows the change, the test evidence, the exact diff, the commits that will be published (verbatim), the findings (each recommended as fix, low-impact, decline or note) and the PR text, then asks before anything is published. It recommends exactly one choice: `Not now` when the no-mistakes validation run ended without passing. Otherwise it recommends `Fix findings first` while a fix finding is neither fixed nor settled (accepted, declined or noted). Otherwise it recommends `Open as a draft` when a draft or human testing is required. Otherwise it recommends `Open the PR`.
- Low-impact findings. A real defect in the changed lines that only rare inputs reach gets the recommendation low-impact instead of fix. It is never a crash, hang, data loss, security problem or failing test. It carries evidence in `impact`: a count from real data when it is cheap to get, or the unusual input it needs. The unusual input alone is enough evidence. The workflow counts a low-impact finding without evidence as fix. The PR's Notes list each one under "Known limitations".
- Autonomy levels, set with the `autonomy` option or `autonomy=<level>` in the request. They apply only at validation gates, which cannot publish. Publishing always waits for the user's approval. An unknown level makes the skill ask and start nothing.
  - `ask`: the user decides every finding, and the skill recommends an action for each one.
  - `minor` (the default): the skill settles low-impact, declined and informational findings on its own, and asks before any fix.
  - `full`: the skill also makes the fixes it recommends, up to the round limit. It asks only for a product decision, or for a fix finding left after the limit.
- `rounds=N` (1 to 5, default 2) caps the fix rounds the skill requests in one run. A fix round is one `--action fix` answer on the no-mistakes gate, or one `Fix findings first` pass on the built-in gate. After the cap, the skill settles the remaining low-impact, declined and informational findings, and asks the user about any fix finding. At `ask` and `minor`, the cap is advisory: past it, the skill recommends settling instead of another fix round. The cap never changes the recommendation for a crash, hang, data loss, security problem or failing test: those stay fix. A value outside 1 to 5 makes the skill ask and start nothing.
- A decision log, `.resolve-issue/decisions.json`, records each finding's decision, who made it and why. When the gate lists a finding again, the skill applies the logged decision instead of asking again. In the publish run, it still shows the finding and waits. The skill keeps one intent block at the end of `intent.txt`, headed `Findings already decided (decisions, not omissions):`. The publish run's review then treats those findings as deliberate.
- A publish flow that runs only after explicit approval, and `/resolve-issue publish <worktree or issue URL>` to publish a run from a later session. Publishing later first re-checks that the issue is still free. It stops when the user already has an open PR from `fix/issue-<n>`, or one that holds the run's commits. The flow checks that the fork is a fork of the upstream repository, and pushes with the `gh` login without waiting for a password. A non-interactive session shows the packet and publishes nothing.
- A fork check before the no-mistakes publish run, for a push target other than the repository itself. The skill creates the user's fork when it does not exist yet, covered by the publish approval. It stops and asks when the target is not a fork of the repository, or does not exist and belongs to another account.
- A publish guard: `PreToolUse` hooks that block `git push`, GitHub writes (`gh` and its `gh-axi` wrapper, `curl`, `wget`, `hub`, and GitHub MCP tools whose names start with a write verb, listed in docs/safety.md) and publishing no-mistakes runs. For `gh`, every subcommand of a group that can write counts unless it is a read, so gh's own aliases (`gh pr new`) and newer subcommands count too. A `curl` or `wget` write counts only when its request URL is on GitHub, not when a body or header names GitHub. An MCP tool whose input has a `command` string (a shell tool) has that string read like a Bash command, in the session's working directory; a command given as a list, arguments in another field and the tool's own working directory are not read. Any other MCP tool is judged by its name alone, whatever the size of its input.
  - Run rule: a hook on the Workflow tool records the session when the pipeline starts or resumes, triage included. For 12 hours after that, the guard denies every publishing command it sees from any subagent in that session, wherever the command runs. This covers recon. Nothing clears the record when the run ends; docs/troubleshooting.md says how to lift it early.
  - Worktree rule: in a resolve-issue worktree, the guard denies every publishing command it sees from a subagent, and the main session needs a one-time token. A token covers one tool call (all of that call's hook processes share it) and expires after 15 minutes. The worktree step removes any old token.
  - Unknown-directory rule: a subagent's publishing command whose directory cannot be resolved (a variable, a command substitution, a folder that does not exist yet) is denied in every session and repository while the guard is on.
  - Over-limit rule: a command nested more than 16 levels deep, with more than 64 KB (65,536 bytes) of text to read, with more than 1,024 subshells and directory changes, with more than 64 publishing commands, or that names programs so often that checking it would read more than 200,000 words is not read past that point. A subagent may not run it, in any session; the main session's is judged in the directory where reading stopped. The bounds keep the hook well inside its 15-second timeout.
  - The token is a speed bump for the main session, not proof of approval. The skill creates it only after the user approves. The one exception applies at autonomy `minor` or `full`. The skill then creates a token for one `no-mistakes axi respond` on a validation run. The run qualifies only when the workflow or the skill started it with push, pr and ci skipped, and none of those steps has run.
  - The parser finds `git`, `gh`, `gh-axi`, `no-mistakes`, `curl`, `wget` and `hub` at any word position, so keywords and wrappers with options do not hide them, and skips the arguments of programs that never run them, such as `echo` and `grep`. It joins backslash-newline continuations, drops comments, and treats heredoc bodies as data unless a shell named in the heredoc's own command (for a heredoc on a loop's or group's closer, its whole line), or later on its line, can run them. It reads through `sh -c`, `bash -c`, `zsh -c` (after options such as `-o pipefail`), `eval`, `env -S`, a here-string given to a shell and a `$( )` inside double quotes, and reads a program computed at run time like `git`. A help request such as `git push --help` is not publishing. It follows `cd`, `cd -`, `pushd` and `popd` in the order they are written. A `cd` inside a subshell, or behind a wrapper that starts a program of its own (`env cd`), does not change the directory of later commands; one in the text of `eval` does. If the parser itself fails, the command is blocked.
  - It is meant to catch publishing that agents do by mistake. It reads the command text, so publishing inside a script file, a Makefile target or a git alias from the user's config is not seen, nor is text computed while the command runs. It does not evaluate conditions, loops, functions, pipelines or background jobs, so a command written to get past it can. It does not cover other tools, or the main session outside resolve-issue worktrees, when a command's directory cannot be resolved, or past a bound. It is defense in depth, not a sandbox.
- Plugin options: `default_mode`, `default_effort`, `confirm_before_run`, `publish_guard` and `autonomy`.
- Resumable stops: a stopped run continues from cache with `resumeFromRunId`, in the Claude Code session that started it, except verdict stops such as `invalid-issue` or `infeasible`, which say they are final. A resume can name the steps to run again: the `retryNodes` map after `agent-failed`, `validateAttempt`, the `confirmAttempts` map after `tree-damaged`, `gateAttempt` for the final check, and `scopeDecisions`. The maps keep every earlier entry, so a later stop never reverts an earlier one. Optional steps (the polish review and apply, and the extra reviewers) are not retried, so skipping one is respected. Steps that run side by side (the three recon agents, and the contribution-rules reader beside the worktree and validation steps) make their single retry after they all return, in a fixed order, so a resume replays them and every later step from cache. The skill saves the run ID and the latest launch arguments in `.resolve-issue/packet.json` while the worktree exists. In another session, it offers a fresh run from them (or from the request when no packet.json exists), with the change the stop asked for when it is `force`, a larger `attempts` or `maxAgents`, or `gate=builtin`. A saved `force` is kept only when that stop asks for it, and resume-only arguments are left out, so a scope question may be asked again. It asks the cost question first, unless that is turned off or the request said `yes`.
- Commands the skill suggests use `/resolve-issue:resolve-issue` when the user invoked it that way.
- Requirements: git 2.31 or later; the no-mistakes publish step's upstream check needs git 2.38 or later and treats older git as a conflict. The no-mistakes gate needs no-mistakes v1.84.0 or later.
